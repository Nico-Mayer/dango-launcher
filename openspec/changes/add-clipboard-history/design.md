## Context

The extension contract now has everything this needs except two things nobody
has built: reading a preference, and a service that writes to the database while
the user works. `applications` has a service, but it only rebuilds an index it
owns; it never reacts to the user.

The store already has a `preferences` table with a unique index over
`(extension_id, command_id, key)`, written in M1's first migration. Nothing has
ever read or written a row in it. `extension-model` already requires that an
unset preference reads back its declared default, so that behaviour is specified
and unimplemented rather than new.

Images are the first content that is not a string. The icon cache already writes
PNGs to the cache directory and serves them to the webview through the asset
protocol, so the mechanics exist; what is new is that the content is the user's,
not the system's, and deleting it has to actually delete it.

## Goals / Non-Goals

**Goals:**

- Never record something the user would be alarmed to find recorded. A miss is
  a nuisance; a leaked password is the feature being a liability.
- Bounds that hold without the user thinking about them.
- Preference reading that every later extension can use, not a shape that only
  suits an exclusion list.

**Non-Goals:**

- No paste, no preferences UI, no sync. See the proposal's non-goals.
- No attempt to capture what was copied while Dango was not running. There is no
  such record to read on either platform.

## Decisions

### Poll a sequence counter on both platforms

Both systems expose a cheap monotonic counter that changes when the clipboard
does: `NSPasteboard.changeCount` and `GetClipboardSequenceNumber`. The watcher
reads it on a short interval and only touches the clipboard's contents when it
moves.

Rejected: `AddClipboardFormatListener` on Windows, which is genuinely
event-driven. It needs a message-only window and a message pump on a thread that
owns it, which is a second concurrency model in the codebase for one extension,
and it has no macOS counterpart, so the shared service would still need the
polling path. One mechanism on both platforms is worth more here than the
milliseconds an event saves.

Rejected: polling the contents rather than the counter. Reading the clipboard
proper is expensive and, on macOS, reading it is observable by other
applications; a launcher should not be seen touching the clipboard several times
a second.

### Exclusion is checked before the content is read, not after

The privacy markers are their own clipboard types. The watcher asks whether any
of them is present before it reads text or image data at all, so excluded
content is never in Dango's memory.

macOS looks for `org.nspasteboard.ConcealedType`, the convention password
managers follow, and treats
`org.nspasteboard.AutoGeneratedType` the same way. Windows looks for the
`ExcludeClipboardContentFromMonitorProcessing` and `CanIncludeInClipboardHistory`
formats.

### The copying application is identified differently per platform, and macOS is approximate

Windows can name the owner: `GetClipboardOwner` gives a window, and the window
gives a process. macOS cannot; `NSPasteboard` does not record who wrote to it.
There the watcher uses the frontmost application at the moment the change was
noticed.

This is approximate, and the design says so rather than implying otherwise: if
the user switches applications within the poll interval, the wrong application
is attributed. The consequence is bounded because the marker check, which is
exact, runs first and is what password managers actually set. The exclusion list
is the backstop for applications that set no marker.

### Retention bounds are preferences, with defaults that hold on their own

Entry count, per-entry size ceiling, and total size ceiling are declared
preferences with defaults of 500 entries, 16 MB, and 256 MB. That makes the
first real consumer of the preference plumbing something other than the
exclusion list, which is worth having before the shape is fixed.

Rejected: constants. The bounds are exactly the kind of thing the author will
want to change after living with it, and a preference costs nothing here because
the reading path is being built anyway.

### Reading a preference needs the declaration, so it is not a bare store call

Returning the declared default requires knowing the declaration, which lives in
the manifest, not the database. So the store gains typed get and set keyed on
scope, and the extension host hands an extension a reader bound to its own
manifest. An extension cannot read another extension's preferences by
construction rather than by convention.

A stored value that no longer parses as its declared type reads back as the
default. The alternative, refusing to load the extension, punishes the user for
a schema change they did not make.

### Text in the database, images as files

Text entries hold their content in the row. Image entries hold a path to a PNG
in the cache directory, written by the same helper the icon cache uses.

Rejected: image blobs in SQLite. It bloats the database file that also holds
preferences and frecency, it makes the size ceiling a `VACUUM` problem, and the
webview cannot render a blob without a round trip through the backend, while it
can already load a file through the asset protocol.

The consequence to get right is deletion: discarding an image entry has to
delete its file, and so does removing one by hand. A row without its file is the
failure the spec names, and it resolves by dropping the row.

### The history is machine-local

It uses the `local_` table convention, so it is excluded from sync by
construction. Two machines agreeing on clipboard history is not a feature
anyone asked for, and it would put every password a marker failed to catch onto
a second machine.

### Dango's own writes are skipped by counter, not by content

After putting an entry back on the clipboard, the watcher records the sequence
number that write produced and ignores exactly that one. Comparing content
instead would also swallow the user genuinely re-copying the same thing from
another application.

### The view is the existing list, with the thumbnail in the icon slot

No protocol change. An image entry sets `icon` to its PNG path, which the
renderer already turns into an asset URL; a text entry sets a named icon. The
row height may need to grow for a thumbnail to be worth showing, which is a
styling change in `ProtocolView`, not a contract change.

## Risks / Trade-offs

- **A password manager that sets no marker and is not on the list will be
  recorded.** → The exclusion list exists for exactly that, but it is only as
  good as what the user puts in it, and until M7 there is no UI to put anything
  in it. Documented rather than solved.
- **Polling has a window.** Something copied and replaced within the interval is
  missed entirely. → Accepted; the alternative is the Windows-only event route
  and a second concurrency model.
- **macOS attribution is approximate.** → Bounded by the marker check running
  first. Recorded above.
- **The size ceiling is enforced after writing, not before.** The image has to
  be encoded to know how big it is. → Transient overshoot of one entry, which
  the per-entry ceiling already bounds.
- **A service that writes while the user works is new.** The indexing service
  writes on its own schedule; this one writes in response to the user and could
  contend with a search reading frecency. → SQLite handles the concurrency, and
  the write is small and off the activation path, but it is the first time two
  things write during normal use and is worth watching in verification.

## Open Questions

- Whether a text entry should record which application it came from and show it
  as a subtitle. Deferred: it changes no spec here, the attribution is already
  being computed for the exclusion check, and it is a subtitle string if the
  author wants it.
